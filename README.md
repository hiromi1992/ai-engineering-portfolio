## 30秒で分かること

私は開発PMとして、**事業として実現したい内容や顧客要望を整理し、プロダクトの要件・仕様に落とし込み、開発を進め、リリース後の結果を見ながら改善する**ところを主に経験してきました。

現在はそこから一歩進めて、個人開発で以下まで自分の設計範囲を広げています。

- データ構造と責任分界
- AIエージェントへ任せる範囲と、人・ルールで止める境界
- 根拠・反証・不確実性の管理
- 状態管理、再試行、復旧
- 評価条件、未使用データ、独立レビュー
- AIの自己申告ではなく、実状態を確認したうえでの受入判断

**Codex / Claude等を実装支援に使いながら、問題設定、要件、設計方針、テスト・評価観点、Gitや実状態の確認、受入・再設計まで自分で担っています。**

## 現在の主力開発

### 1. [Signal Harvester / ICP](projects/02_signal_harvester.md)

**WebやGitHub等から得た情報を、出典・時点・反証・不確実性・履歴を失わずに、後続のAIや分析へ渡す情報基盤です。**

複数の収集処理を独立して動かし、1回の実行ごとに追記型で記録します。各観測候補には、情報源、発生時刻と観測時刻、支持材料、反証、未知事項、新規・更新・重複関係などを持たせます。

ICPで集めた情報をそのまま確定事実にはせず、**検証済みのものだけをSignal Harvester側の正式な観測・根拠・シグナルへ昇格**する責任分界にしています。

- 非公開の現行開発リポジトリで主要機能を実装・検証済み
- 観測範囲を継続拡張中
- 公開側には、候補→検証→昇格の簡略モデルと根拠再検証コードを掲載

→ [ICPの候補→検証→昇格モデル](samples/icp_data_model.js)

### 2. [AI開発基盤 / Review-Handoff Platform](projects/01_ai_development_foundation.md)

**AIへ実装を任せた後、AI自身の完了報告ではなく、Git・テスト・実際の変更内容から受入可否を判断する共通基盤です。**

成功・失敗だけでなく**結果不明**を独立した状態として扱い、確認前の再実行を止めます。重要な変更では、自動テストの後に独立レビューを追加し、必要なら実装だけでなく設計・要件まで戻します。

- 非公開の現行開発リポジトリで主要機能を実装・検証済み
- 安全条件を確認できない自動実行は制限
- 古いGit状態、範囲外変更、結果不明時の再実行などを検証

→ [AI実装結果を安全に適用する公開サンプル](samples/result_apply_guard.py)

## 代表的な設計判断

| 課題 | 設計判断 |
|---|---|
| AIが「完了」と言っても実際には反映されていない | 実ファイル・Git・テストを読み戻して完了判定 |
| 同じ情報の転載を複数の独立根拠として数えてしまう | 情報源・出所・重複関係を分離して保持 |
| AIが支持材料だけを集めて結論へ寄る | 反証・不確実性・未知事項も別項目で保持 |
| 「情報が0件」と「そもそも見ていない」を混同する | 欠測理由を状態として保持 |
| 外部操作の結果が分からないまま再実行してしまう | 結果不明を独立状態として自動再試行を停止 |
| 結果を見た後に条件を変えて評価を歪める | 未使用データ・評価条件・観測履歴を分離 |
